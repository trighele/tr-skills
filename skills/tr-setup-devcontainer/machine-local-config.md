# Machine-local config: keeping host specifics out of git

The `${localEnv:USERPROFILE}${localEnv:HOME}` trick in [claude-in-container.md](./claude-in-container.md) absorbs *home directory* differences and nothing else. It works, it needs no setup, and for a simple single-container project it is enough — reach for it first.

It runs out when a machine differs in a way an env-var concatenation cannot express:

- **Paths that aren't derived from `$HOME`.** The gh CLI config is `%APPDATA%\GitHub CLI` on Windows and `~/.config/gh` on macOS. There is no one expression for both.
- **The base image itself.** A corporate-registry image (`*.artifactory.example.com/...`) is unpullable from a personal machine. The `FROM` line is machine-specific.
- **uid/gid.** Windows has no host uid to match; macOS and Linux do, and getting it wrong means bind-mounted files aren't writable.
- **Architecture.** An amd64-only corporate image needs `platform: linux/amd64` pinned on Apple Silicon and nothing on an amd64 host.
- **Secrets.** Anything that must never be committed, sitting right next to the config that must be.

`devcontainer.json` cannot compute any of that, and `${localEnv:}` doesn't work in a compose file at all. When two or more of the above are in play, use this pattern.

## The pattern: gitignored `.env` + `initializeCommand` bootstrap

One gitignored `.env` per compose file is the single source of truth for that machine. The compose file interpolates from it. A committed, cross-platform bootstrap script generates it, run automatically by `initializeCommand` — which executes **on the host, before the container is created**, which is exactly the hook this needs.

```
.devcontainer/
  bootstrap.mjs              committed — detects the host, writes the .env
  post-create.sh             committed — shared postCreateCommand
  .dockerignore              committed — keeps .env out of the build context
  <target>/
    devcontainer.json        committed — contains no host paths at all
    docker-compose.local.yml committed — reads ${HOST_HOME}, ${BASE_IMAGE}, ${HOST_UID}
    Dockerfile               committed — FROM ${BASE_IMAGE}
    .env.example             committed — template, blank secrets
    .env                     GITIGNORED, generated
```

Node is the right language for the bootstrap when the repo already has it: one script, no `.ps1`/`.sh` pair to keep in sync, and `os.homedir()` / `process.platform` / `process.getuid` give everything needed. Use a `.ps1` + `.sh` pair only for a repo with no Node.

```jsonc
// ARRAY form, not string. Each element is passed as one argument verbatim, with
// no shell involved.
"initializeCommand": ["node", "${localWorkspaceFolder}/.devcontainer/bootstrap.mjs", "<target>"],
"postCreateCommand": "bash .devcontainer/post-create.sh"
```

**Use the array form for `initializeCommand`, always.** The string form is re-quoted by the extension when it spawns a shell on the host, and quotes around a Windows path end up *inside* `argv`:

```
Error: Cannot find module 'c:\repo\project\"c:\repo\project\.devcontainer\bootstrap.mjs"'
```

Note the doubled path — the quoted string was treated as a relative path and joined to the cwd. It is tempting to diagnose this as cmd.exe mishandling the quotes, but running the same `cmd.exe /c node "<path>" <arg>` line by hand works fine; the mangling happens in the spawn, so escaping harder does not fix it. The array form does, and it needs no escaping at all.

Incidentally, that error also proves the working directory of `initializeCommand` is the workspace folder, so a relative path works too. Prefer `${localWorkspaceFolder}` anyway — it is explicit and survives the extension changing its mind.

```yaml
# docker-compose.local.yml — ${VAR:?msg} fails fast with a readable message
# instead of silently mounting an empty path if the bootstrap never ran.
services:
    local-dev:
        build:
            args:
                BASE_IMAGE: ${BASE_IMAGE:?run "node .devcontainer/bootstrap.mjs <target>" first}
                USER_ID: ${HOST_UID:-1000}
        platform: ${DOCKER_PLATFORM:-linux/amd64}
        volumes:
            - ../..:/workspace:cached
            - ${HOST_HOME:?run the bootstrap first}/.claude:/home/vscode/.claude
        env_file:
            - path: .env
              required: false
```

The `${VAR:?message}` guard is the load-bearing detail. Without it a missing `.env` silently yields `source=/.claude`, Docker helpfully creates an empty directory, and the symptom is "my skills vanished" three steps later.

## Rules for the bootstrap script

**Rewrite only a marked block.** The `.env` usually already holds hand-entered secrets. Delimit the generated region and replace only that:

```
# >>> devcontainer machine config — generated by bootstrap.mjs, do not edit >>>
...
# <<< devcontainer machine config <<<
```

Read the file, cut from `BEGIN` to `END`, append the fresh block, write. Verify idempotency by running it three times and diffing — a marker bug that appends instead of replacing is easy to write and annoying to notice.

**Write the block last.** Compose's dotenv parser takes the final assignment of a key, so a trailing block means generated values win over stale hand-edited ones.

**Write the block with LF even when the file is CRLF.** A `.env` edited on Windows is often CRLF. Mixed endings are fine — parsers strip `\r` — but a trailing `\r` on `HOST_HOME` corrupts every volume path derived from it. Don't match the surrounding file's endings; force LF.

**Normalise Windows paths to forward slashes.** `os.homedir()` returns `C:\Users\x`; a backslash in a compose volume path is ambiguous. `C:/Users/x` works on every platform.

**Emit only proxy variables that are actually set.** A defined-but-empty `HTTP_PROXY` breaks tools that test for presence rather than value. Same rule as [proxy-and-certs.md](./proxy-and-certs.md).

**Seed from `.env.example` when `.env` is absent**, so a fresh clone gets the shape of the secrets it needs with blank values.

**Warn on things that should exist and don't** — `~/.claude` above all. A warning on the host is far cheaper to act on than an empty mount discovered inside the container.

**Add a `.dockerignore` for `**/.env`** if the build context contains it. Secrets should not be shipped to the daemon.

## Git identity: prefer an env var over mounting `~/.gitconfig`

[git-parity.md](./git-parity.md) mounts the host `.gitconfig` read-only and copies the identity out of it. With this pattern there's a simpler route: have the bootstrap read the identity on the host and write it into the `.env`.

```js
GIT_USER_NAME=<git config --get user.name>
GIT_USER_EMAIL=<git config --get user.email>
```

```bash
# post-create.sh
if [ -n "${GIT_USER_NAME:-}" ];  then git config --global user.name  "$GIT_USER_NAME";  fi
if [ -n "${GIT_USER_EMAIL:-}" ]; then git config --global user.email "$GIT_USER_EMAIL"; fi
```

This removes a file bind mount that silently becomes an empty *directory* if the source doesn't exist, and it never risks pulling in a Windows-only credential helper. Push credentials come from the Dev Containers extension's own forwarding either way, so nothing is lost.

## Multiple containers in one repo

A polyglot repo may genuinely need two images — say a Node/Python one and a .NET one. Then `.devcontainer/` holds a folder per container, each with its own `devcontainer.json`, compose file, `Dockerfile` and `.env`. VS Code offers the choice on "Reopen in Container".

Keep the bootstrap and the `postCreateCommand` script **shared at `.devcontainer/` level**, with a per-target table inside the bootstrap for the things that differ (base image, fallback uid/gid). Duplicating them is how they drift.

To let two Dockerfiles `COPY` the same shared script, set the compose build context to `.devcontainer/` rather than the per-target folder, and make the `dockerfile` and every `COPY` path relative to it:

```yaml
build:
    context: ..
    dockerfile: <target>/Dockerfile
```

```dockerfile
COPY ./<target>/odbcinst.ini /etc/odbcinst.ini
COPY ./install-claude-code.sh /tmp/
```

Forgetting to re-root the existing `COPY` paths after widening the context is the one thing that breaks here, and the error (`file not found`) is at least clear.

## Shared repos: degrade gracefully for people who aren't you

A `.devcontainer/` committed to a team repo is used by people who do not have your tools, your
secrets, or your corporate agents. Every host-dependent mount and credential must therefore have a
defined behaviour when it is absent, and that behaviour must not be "quietly break something".

**A bind mount with a missing source is not skipped — Docker CREATES the source.** For a directory
source you get an empty directory; for a **file** source you get a **directory where a file should
be**. This is the sharpest edge in the whole skill:

```jsonc
// On a machine without Claude Code, this leaves a DIRECTORY named
// .claude.json in that person's home. Claude Code then breaks if they
// ever install it — and the cause is invisible.
"${localEnv:HOME}/.claude.json:/home/vscode/.claude-host.json:ro"
```

Compose cannot express a conditional mount, so resolve the path in the bootstrap and point at a
placeholder when the real thing is absent:

```js
mkdirSync(path.join(LOCAL_DIR, 'empty-claude'), { recursive: true });
if (!existsSync(placeholderJson)) writeFileSync(placeholderJson, '{}\n');
return { dir: hasDir ? hostDir : placeholderDir,
         json: hasJson ? hostJson : placeholderJson,
         present: false };
```

Put placeholders in a gitignored `.devcontainer/.local/`, never in someone's home directory. Also
emit a `HOST_HAS_*` flag so `postCreateCommand` can tell "this person doesn't use the tool" apart
from "the mount is broken" — those need opposite messages, and guessing wrong is how a working
container gets reported as broken.

**Verify it by simulating the other developer**, not by reasoning about it:

```sh
FAKE=/tmp/fakehome; rm -rf $FAKE; mkdir -p $FAKE
USERPROFILE="$FAKE" HOME="$FAKE" node .devcontainer/bootstrap.mjs
ls -la "$FAKE"     # must still be empty — nothing created in their home
```

**Calibrate the severity of every message.** An optional credential that a .NET-only developer will
never need should not print a warning that reads like a failure. Say what it is for and who needs
it. Conversely, a genuinely fatal prerequisite deserves a table entry in the README — for a
bootstrap invoked from `initializeCommand`, "the host needs Node" is a hard requirement that will
otherwise surface as an opaque startup error.

Checklist before handing a shared devcontainer over:

- Optional tool absent → placeholder, informational message, container still starts.
- Optional credential absent → informational message naming what it unlocks, not a warning.
- Required prerequisite absent → documented in the README with the symptom.
- Nothing is created in the user's home directory that they did not ask for.
- No host path, secret, or personal identifier is committed.

## Verify

```sh
node .devcontainer/bootstrap.mjs                          # inspect the generated .env
docker compose -f docker-compose.local.yml config          # all vars resolve?
mv .env .env.bak && docker compose ... config; mv .env.bak .env   # guard message fires?
git status --short                                         # .env must NOT appear
```

That last one is the whole point of the exercise — check it explicitly.
